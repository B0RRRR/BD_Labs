## 1. Как делается технический проект (подраздел 3.1)

**Что это.** Стадия разработки по ГОСТ 19.102 (ТЗ → эскизный проект → **технический проект** → рабочий проект → внедрение).
Принципиальные компоненты архитектуры разбиваются на технические программные компоненты, и для каждого выбирается способ реализации.

- **Вход:** требования ТН, ФТ, ФТТ, ТТ (2.1) и архитектура (2.6): компоненты К1–К6, ИР, ПФ, ПР.
- **Выход:** таблица технических компонентов (solution).

**Порядок:**
1. Каждый компонент разбить по его подпроцессам (DFD-2):
   - данные → таблицы;
   - правила → ограничения и триггеры;
   - операции → функции;
   - выдача информации → запросы и представления;
   - обмен с окружением → интеграция и планировщик.
2. Выбрать способ реализации по ПФ:
   - правило, выразимое декларативно → CHECK / FK / UNIQUE / EXCLUDE;
   - иначе → триггер. Пример: ёмкость спринта — это сумма по многим строкам, CHECK её не видит, поэтому нужен триггер с `FOR UPDATE` (PM004);
   - составная операция → функция в одной транзакции (`create_project`, `close_sprint`);
   - частый агрегат → материализованное представление (`mv_project_stats`).
3. Уточнить физическую модель (3.3) и алгоритмы сложных модулей: модуль 10, модель времени подзапроса (2.5.5, 3.7).
4. Разбить структуру на миграции 001–013 и задать порядок развёртывания: `init.sh`.
5. Каждому техническому компоненту сопоставить требования и испытания (таблица ФТ). Это вход для ПМИ.

**Пример по одному компоненту.** К4 «Задачи» →
- таблицы: `tasks`, `sprints`, `marks`, `task_status_history`;
- триггеры: жизненный цикл, история, ёмкость, аудит;
- функции: `close_sprint`, `import_tasks`.

**Возможные вопросы:**
- *Чем технический проект отличается от архитектуры?*
  - Архитектура отвечает на вопросы «что» и «почему»: принципиальные компоненты, принципы ПФ и ПР.
  - Технический проект отвечает на вопрос «как»: конкретные таблицы, функции, триггеры и способ реализации каждого.
- *Что делается на стадии технического проекта по ГОСТ 19.102?*
  - уточняются входные и выходные данные;
  - разрабатываются алгоритмы и структура программы;
  - определяется конфигурация технических средств;
  - составляется план разработки и внедрения.

## 2. Как создаётся ПМИ (подраздел 4.1)

**Состав документа по ГОСТ 19.301:**
- объект испытаний;
- цель;
- требования к программе;
- требования к документации;
- средства и порядок испытаний;
- методы испытаний.

**Порядок:**
1. Составить перечень проверяемых свойств:
   - 33 требования: ТН-1–3, ФТ-1–21, ФТТ-1–4, ТТ-1–5;
   - 7 критериев К1–К7.
2. Для каждого свойства задать испытание: сценарий, исходные данные, ожидаемый результат (эталон по контрольным данным). Некорректные операции подобрать так, чтобы каждое ограничение и каждый код PM проверялись хотя бы раз.
3. Определить состав обстоятельств и критерии приёмки.
4. Занести требования, критерии, испытания и их связи в базу данных качества (схема `quality`). Ещё **до** испытаний `v_requirements` показывает требования, которые ничем не проверяются.
5. После готовности приложения провести прогон: записать фактические результаты (`test_results`) и значения критериев (`criterion_values`); `v_runs` выдаст решение о приёмке.

**Состав обстоятельств, обусловливающих успешное проведение испытаний** (что и зачем):

| Обстоятельство | Зачем |
|---|---|
| Среда: PostgreSQL 16.15, Ubuntu (WSL2), `psql`; база разворачивается с нуля `init.sh` | результат не зависит от чужой конфигурации |
| Данные: контрольный набор (эталоны известны заранее), демонстрационный, нагрузочный 100 000 задач | для каждой проверки есть данные с известным ответом |
| Изменяющие проверки — на копии базы (`createdb -T`) | испытания не влияют друг на друга, их можно повторить |
| Фиксированная дата 14.11.2026, детерминированный генератор | результат воспроизводим |
| Замеры после прогрева кэша, без посторонней нагрузки, медиана нескольких прогонов | время не искажено случайными факторами |

**Объект, предмет, цель:**
- объект — что испытываем: база `project_mgmt` со сценариями, функциями, триггерами, запросами;
- предмет — какие свойства проверяем: правильность, целостность, атомарность, время модулей, воспроизводимость развёртывания;
- цель — подтвердить требования ТН, ФТ, ФТТ, ТТ.

**Порядок проведения:**
1. подготовка: развёртывание с нуля и миграция заполненной базы (И1, И8);
2. допуск: миграции без ошибок, данные загружены, `v_requirements` не показывает непокрытых требований;
3. функциональные испытания, целостность, транзакции, права — на копиях базы;
4. нагрузочные — на отдельной базе 100 000 задач (И13, И14);
5. регистрация результатов в базе качества и решение о приёмке.

**Приостановка:** схема изменена без миграции, испорчены исходные данные или замер искажён посторонней нагрузкой → база разворачивается заново, повторяются затронутые испытания. После исправления программы (новой миграцией) — новый прогон: И1 и испытания изменённых требований.

**Критерии приёмки:**
- 17 из 17 некорректных операций отклонены;
- нет частичных изменений;
- инвариант ёмкости сохранён;
- запросы совпали с эталоном;
- каждый модуль выполняется ≤ 1 с при 100 000 задач.

**Показать вживую:**
```bash
psql -c "SELECT * FROM quality.v_requirements WHERE NOT covered"   # пусто: все 33 покрыты
```

**Возможные вопросы:**
- *Чем программа отличается от методики?*
  - Программа: что проверяем, в каком составе и порядке, при каких условиях.
  - Методика: как проверяем и как сравниваем факт с ожидаемым (методы, средства, критерии).
- *Как убедились, что будут проверены все требования?* Через `v_requirements`: у всех 33 требований `covered` = true. Выполнены ли они (`satisfied`), станет известно после прогона.
- *Почему не оценено качество при использовании?* В ГОСТ Р ИСО/МЭК 25010 две модели: качество продукта (наши К1–К7) и качество при использовании. Вторую измеряют на работающем приложении с пользователями (доля заданий без помощи, время задания, анкета), поэтому она отложена до приложения.
- *Что будет, если испытание провалится?*
  - `passed = false` → требования этого испытания перестают быть `satisfied`, а прогон — `accepted`.

## 3. Лингвистический минимум (подраздел 1.4)

**Определение.** Минимальный набор понятий (сущностей, атрибутов, связей), достаточный для описания предметной области и функций системы. Лишних понятий нет, и нет функции, для которой понятий не хватает.

**Опора — ГОСТ 34.320-96** (концептуальная схема БД):
- декларативная модель — это концептуальная схема;
- имена сущностей и атрибутов — лексические объекты, связи-глаголы (ВЛАДЕЕТ, ИСПОЛНЯЕТ) — предикаты, правила П1–П18 — предложения;
- принцип 100 %: все правила предметной области описаны в схеме, и за каждое отвечает СУБД.

**База данных** (рисунок Б.1):
- 10 сущностей, 14 связей;
- через них выражены правила П1–П18 и все 35 подпроцессов DFD-2.

**Система оценивания качества** (рисунок Б.2, схема `quality`, миграция 012):
- **сущности:** ТРЕБОВАНИЕ, КРИТЕРИЙ, ИСПЫТАНИЕ, ПРОГОН;
- **связи** (все M : N):
  - ПРОВЕРЯЕТ (испытание — требование);
  - ОЦЕНИВАЕТ (критерий — требование);
  - ВЫПОЛНЯЕТ (прогон — испытание; атрибуты actual, passed);
  - ИЗМЕРЯЕТ (прогон — критерий; атрибут value);
- **производные атрибуты** (пунктирный овал, вычисляются запросом, не хранятся):
  - met — критерий выполнен;
  - covered — требование покрыто;
  - satisfied — требование выполнено;
  - accepted — прогон принят.

## 4. Требования одной строкой (подраздел 2.1)

- **ТН** — требование назначения: зачем система нужна (ТН-1 — единый непротиворечивый учёт).
- **Условия применения:**
  - пользователи;
  - объём 100 000 задач;
  - конкурентная работа;
  - среда PostgreSQL 16;
  - непрерывный режим.
- **ФТ** — что делает система (ФТ-10 — планировать спринт с учётом ёмкости).
- **ФТТ** — как хорошо она это делает: время, атомарность, корректность при конкурентном доступе (ФТТ-1 — модуль ≤ 1 с).
- **ТТ** — на чём и как реализуется: СУБД, нормальная форма, миграции, роли (ТТ-4 — миграции без потери данных).

## 5. Учёт трудозатрат и договор «план/факт» (миграция 013)

**Зачем.** Раньше бюджет договора сравнивался только с оценками задач. Теперь участники списывают фактические часы (`worklogs`: задача, сотрудник, день, часы), и отчёт О2 сравнивает с бюджетом факт.

**Правила (триггер `worklog_guard`):**
- П17 — не больше 24 ч в сутки на сотрудника (PM006). Перед проверкой триггер блокирует строку сотрудника (`FOR NO KEY UPDATE`), как строку спринта при проверке ёмкости. Из двух одновременных списаний по 14 ч за один день первое должно быть записано, а второе — получить PM006;
- П18 — часы списывает участник проекта на задачу в работе или на проверке, за день от создания задачи до сегодня (PM007). Часы выполненной задачи не меняются, сотрудника со списанными часами удалить нельзя (RESTRICT).

**Почему проверка членства — триггер, а не составной FK.** FK потребовал бы хранить в `worklogs` копию `project_id`, то есть вторую денормализацию, и запретил бы исключать участника, у которого есть часы. Триггер проверяет членство на момент списания, а история часов остаётся.

**Формула прогноза (2.5.2):**
- k = F_вып / H_вып — во сколько раз команда тратит больше оценённого;
- H_пр = F_вып + Σ max(f_t, k·e_t) по незавершённым задачам;
- B = H_пр / H_бюдж · 100 %.

**Пример.** Оценки задач составляют 70 % бюджета, а команда тратит в 1,5 раза больше оценённого (k = 1,5). Тогда прогноз — около 105 %, вердикт «перерасход бюджета» ещё до окончания работ.

**Проверки.** `db/demo/worklogs.sql` (испытание И15): ожидается одно успешное списание и 9 отклонённых.


## 6. Разбор записки по разделам

Номера рисунков, таблиц и страниц — по `Пояснительная_записка.pdf` (80 с.; все рисунки — в приложениях: А — функциональная модель (DFD и дерево функций), Б — модели данных, В — BPMN, Г — схемы алгоритмов, Д — архитектура).

### Раздел 1. Анализ предметной области — ЧТО нужно

Логика: слова и правила (1.1) → проблемы (1.2) → что делает система (1.3) → какие данные существуют (1.4) → как мерить качество (1.5) → постановка задачи тремя условиями (1.6). Таблиц БД здесь ещё нет.

- **1.1.** Границы автоматизации: что делает система, а что остаётся за ней (код, вход, доставка почты, финансы, переговоры). Участники (табл. 1), объекты, жизненный цикл задачи `todo → in_progress → review → done`. Главное — правила П1–П18: всё дальнейшее проектирование нужно, чтобы их нельзя было нарушить.
- **1.2.** Табл. 2: проблема → последствие → решение. Объясняет, зачем нужна система.

**Нотация Гейна — Сарсона (приложение А, рис. А.1–А.9):** синий прямоугольник с тенью — внешняя сущность; блок с оранжевой шапкой — процесс; зелёный, открытый справа, — накопитель; стрелка — поток данных.

- **Рис. А.1 — контекстная диаграмма.** Система — один «чёрный ящик» 0, вокруг 6 внешних сущностей (3 человека, 3 сервиса), 16 потоков (в том числе «параметры отчёта» и «перечни и отчёты»). Заказчика нет: он с системой не работает.
- **Рис. А.2 — DFD уровня 1.** Ящик «открыт»: 6 процессов; «один накопитель — одна таблица» (D1 users … D12 comments). Стрелка к накопителю — запись, от накопителя — чтение. Накопители в два ряда со сдвигом — все линии прямые; накопитель, который пишет один процесс и читает соседний (D1, D3, D5, D7), стоит на их границе. Процесс 6 только читает. D8, D9 используются только процессом 4 — они на DFD-2. Балансировка: все 16 потоков рис. А.1 есть и здесь.
- **Рис. А.3 — дерево функций.** Корень — система, 6 функций = процессы DFD (те же номера и названия), 35 атомарных подфункций = подпроцессы DFD-2 (новые номера при разбиении — в конце: 2.7, 4.10–4.13). Дерево — состав действий, DFD — движение данных.
- **Рис. А.4–А.9 — DFD уровня 2 каждого процесса** (подпроцессы = 35 подфункций дерева функций). Номер подпроцесса = номер сервисной задачи BPMN = номер операции компонента К. Процессы 1, 3, 5 — столбец подпроцессов между сущностью и накопителем; 2 и 6 — два ряда подпроцессов, руководитель полосой посередине; 4 (рис. А.7) — тринадцать подпроцессов 4.1–4.13.
- **Балансировка:** поток DFD-1 разделён между подпроцессами: «задачи, спринты» процессу 4 — на одиннадцать потоков, поток участника — на «статус» и «трудозатраты»; у процесса 6 «параметры отчёта» и «перечни и отчёты» — пять пар «параметры — результат». Копии: внешняя сущность с косой чертой в углу, накопитель с чертой слева — чтобы не тянуть линии через схему.

**Нотация Чена (рис. Б.1–Б.2):** прямоугольник — сущность, ромб — связь-глагол, овал — атрибут, подчёркнут — ключ.

- **Рис. Б.1 — ER-модель.** 10 сущностей, 14 связей. 1 : N (у проекта много задач), M : N (УЧАСТВУЕТ), 1 : 1 (ОФОРМЛЕН). Двойная линия — обязательное участие (задача обязана быть в проекте; в спринте — нет, бэклог). Атрибуты у ромба — свойства связи (role у УЧАСТВУЕТ). Двойная рамка — слабая сущность ИЗМЕНЕНИЕ СТАТУСА, двойной ромб — идентифицирующая связь, пунктирное подчёркивание — частичный ключ. Табл. 3 — как каждая связь станет таблицей.
- **Рис. Б.2 — модель системы оценивания качества.** ТРЕБОВАНИЕ, ИСПЫТАНИЕ, КРИТЕРИЙ, ПРОГОН. ПРОВЕРЯЕТ и ОЦЕНИВАЕТ — прослеживаемость; ВЫПОЛНЯЕТ и ИЗМЕРЯЕТ — результаты прогона. Пунктирные овалы вычисляются запросом: covered, satisfied, met, accepted.

- **1.5.** Показатели эффективности (польза для компании) ≠ критерии качества ПО К1–К7 (свойства программы, табл. 4).
- **1.6.** «Дано — требуется» и три условия: время ≤ 1 с, атомарность, ёмкость спринта при одновременной работе. Условия потом становятся ФТТ-1, ФТТ-2, ФТТ-3.

### Раздел 2. Проектирование — КАК устроено

Логика: требования (2.1) → процессы (2.2) → таблицы (2.3) → правила в СУБД (2.4) → методика сложных модулей (2.5) → архитектура (2.6).

- **2.1.** ТН — зачем система; условия применения; ФТ — что уметь; ФТТ — функция + показатель; ТТ — платформа. **Табл. 5 — главная таблица записки**: ФТ → функция → процесс → компонент → испытание.
- **2.2.** Процесс = 7 множеств ⟨входы, выходы, внутренние данные, операции, компоненты, ресурсы, человек⟩; табл. 6. Компоненты K станут архитектурой, ресурсы R — базой.

**BPMN (приложение В, рис. В.1–В.7):** пул — процесс, дорожки — участники; кружок тонкий — начало, толстый — конец; жёлтая задача с человеком — делает человек, синяя с шестерёнкой — система (номер подпроцесса DFD-2); ромб с крестом — «или-или»; пунктир к цилиндру — запись в накопитель. Пунктирная стрелка к хранилищу — запись, от хранилища — чтение; хранилища подписаны номерами накопителей DFD.

- **Рис. В.1 — «Ведение проекта».** Верхний уровень: заказчик — свёрнутый пул; проект → команда → цикл спринтов → закрытие. «Выполнение задачи» — свёрнутый подпроцесс (⊞, ||| — параллельно много), регламентные операции — событийный подпроцесс по таймеру.
