# Рассказ на 5 минут: как спроектирована система

Страницы — по `Пояснительная_записка.pdf` (80 с.). Все рисунки — в приложениях: А — функциональная модель: DFD и дерево функций (с. 63–69), Б — модели данных (с. 70–71), В — BPMN (с. 72–76), Г — схемы алгоритмов (с. 77), Д — архитектура (с. 78–80).

Основной текст — около 5 минут в спокойном темпе. Если время поджимает, пропустить абзацы со звёздочкой (*).

## 0:00–0:30. Задача и порядок проектирования

**Показать:** содержание записки.

«Тема — система управления проектами для компании, которая ведёт внутренние и заказные проекты двухнедельными спринтами. Сейчас учёт ведётся в переписке и таблицах: сведения расходятся, перегрузку спринтов и просрочки замечают поздно. Главная идея: все бизнес-правила — восемнадцать правил П1–П18 — проверяет сама СУБД, поэтому их нельзя обойти.

Проектировали сверху вниз: словесное описание и правила, затем что делает система — DFD, какие данные существуют — ER, как выполняются процессы — BPMN, потом таблицы, архитектура, технический проект и методика испытаний. Модели связаны одной нумерацией, поэтому покажу их по порядку.»

## 0:30–1:45. Функциональная модель — приложение А

**Показать рис. А.1 (с. 63)** — контекстная диаграмма.

«Контекстная диаграмма показывает границы: система — один процесс, вокруг шесть внешних сущностей: три роли — администратор, руководитель, участник — и три корпоративных сервиса: каталог сотрудников, Git-хостинг и сервис уведомлений. Всего шестнадцать потоков. Заказчика здесь нет намеренно: с системой он не работает, отчёт получает письмом через сервис уведомлений.»

**Показать рис. А.2 (с. 64)** — DFD уровня 1.

«DFD первого уровня открывает систему: шесть процессов — регистрация, проекты и договоры, состав команды, задачи и спринты, обсуждения, отчёты. Накопители построены по правилу „один накопитель — одна таблица“: от D1 „Пользователи“ до D12 „Комментарии“. Все шестнадцать потоков контекстной диаграммы есть и здесь — уровни сбалансированы.»

**Показать рис. А.3 (с. 65)** — дерево функций, **затем А.7 (с. 68)** — DFD уровня 2 процесса 4.

«Состав функций сведён в дерево: шесть функций — это процессы DFD, тридцать пять атомарных подфункций — подпроцессы второго уровня: у каждой один инициатор, один момент, одни правила и накопители. Каждый процесс разложен на свою DFD второго уровня. Например, у процесса 4 поток руководителя „задачи и спринты“ разделён на одиннадцать потоков к подпроцессам, а поток участника — на „статус“ и „трудозатраты“. Номер подпроцесса проходит через все модели: он же номер сервисной задачи в BPMN и операции компонента в архитектуре.»

## 1:45–2:30. Модели данных — приложение Б

**Показать рис. Б.1 (с. 70)** — ER-диаграмма Чена.

«Декларативная модель в нотации Чена: десять сущностей и пятнадцать связей. Здесь есть все виды связей: один к одному — проект и договор, многие ко многим с атрибутом — участие в команде с ролью, слабая сущность — изменение статуса, которое существует только вместе с задачей. Сущности, связи и правила образуют лингвистический минимум базы данных.»

(*) «Ниже — такая же модель для системы оценивания качества: требование, критерий, испытание, прогон. По ней база сама показывает, все ли требования покрыты испытаниями.»

**Показать рис. Б.3 (с. 71)** — логическая модель.

«Логическая модель — переход к таблицам: двенадцать таблиц в третьей нормальной форме. Одна обоснованная денормализация — заказчик в договоре: так правило „договор заключён с заказчиком проекта“ проверяет составной внешний ключ, без триггера. На линиях подписаны действия при удалении: каскад, запрет или обнуление ссылки.»

## 2:30–3:30. Процессная модель — приложение В

**Показать рис. В.1 (с. 72)** — обзорная BPMN.

«Обзорная BPMN — весь проект. Заказчик — свёрнутый пул: с компанией он обменивается только договором, бэклогом и отчётом. После создания проекта и команды повторяется цикл спринтов. Выполнение задачи свёрнуто в подпроцесс с маркером множества экземпляров, а регламентные операции запускает таймер.»

**Показать рис. В.5 (с. 75)** — «Выполнение задачи».

«Главный процесс — выполнение задачи: в нём почти все правила системы. Четыре дорожки: руководитель, исполнитель, тестировщик и система. Синие задачи выполняет СУБД, и они пронумерованы по подпроцессам DFD. Молния на задаче с проверкой ёмкости — подпроцесс 4.13 — граничная ошибка „ёмкость превышена“: срабатывает триггер с кодом PM004, и поток возвращается руководителю. Часы на задаче исполнителя — таймер „срок прошёл“: эскалация, при которой система повышает приоритет — 4.11, не прерывая работу. Пунктир к цилиндрам — запись и чтение накопителей D7 и D12.»

**Показать рис. В.3 (с. 73)** — процесс 2.

«Остальные процессы построены по одной схеме: выбор операции, действие человека, сервисная задача, хранилище. Каждая молния — реальное ограничение базы: уникальность, запрет удаления, проверка CHECK. В процессе 2 создание проекта с договором — транзакция, двойная рамка: при ошибке откатывается всё.»

## 3:30–4:20. Архитектура и алгоритмы — приложения Д и Г

**Показать рис. Д.1 (с. 78)** — окружение.

«Схема окружения — путь одной задачи в десять шагов: каталог передаёт сотрудника, руководитель создаёт задачу SHOP-42, коммит с ключом задачи через веб-хук переводит её на проверку, а раз в неделю заказчик получает отчёт.»

**Показать рис. Д.2 (с. 79)** — компоненты.

«Главная схема архитектуры: компоненты К1–К6 — это процессы 1–6, операции внутри пронумерованы по подпроцессам. В центре одна база с накопителями D1–D12: каждый компонент пишет свои и читает чужие. Стрелки „З“ — вход из окружения, „О“ — выход.»

(*) **Показать рис. Д.3 (с. 80).** «Контейнеры по C4: веб-интерфейс, REST API на FastAPI, модуль интеграции и PostgreSQL; всё поднимается Docker Compose, а приложение ходит в базу отдельной ролью с минимальными правами.»

(*) **Показать рис. Г.2 (с. 77).** «Самый медленный модуль нашли по модели времени: в запросе 10 подзапросы стоят внутри цикла — это видно на схеме алгоритма по ГОСТ 19.701. Без индексов — порядка десяти секунд, с индексами по внешним ключам ожидаем меньше секунды.»

## Вопросы по диаграммам

- **Почему заказчика нет на DFD?** Он не обменивается данными с системой: требования передаёт руководителю, отчёт получает через сервис уведомлений.
- **Что такое балансировка?** Все потоки процесса верхнего уровня есть на его детальной диаграмме; на нижнем уровне поток можно разделить, но нельзя потерять.
- **Зачем «один накопитель — одна таблица»?** DFD напрямую соответствует базе (правило согласованности С3): видно, какой процесс пишет таблицу, а какой только читает.
- **Чем BPMN отличается от DFD?** DFD показывает, какие данные и куда передаются; BPMN — порядок действий, исполнителей, ветвления и события.
- **Почему главный процесс — задача, а не проект?** Проект — верхний уровень (В.1), он складывается из процессов 1–6; в выполнении задачи сосредоточены почти все правила, поэтому оно детализировано отдельно.
- **Что такое граничное событие?** Событие на рамке задачи: ошибка прерывает задачу и уводит поток, таймер с пунктирной рамкой запускает ветку, не прерывая работу.
